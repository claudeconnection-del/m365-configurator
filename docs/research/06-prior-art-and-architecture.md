# Research 06 — Open-source prior art & a candidate architecture

> **Scope.** Survey the open-source tools that already assess, report on, or
> configure Microsoft 365 security posture — **ScubaGear**, **Maester**,
> **Monkey365**, **Microsoft365DSC**, and (as a contrasting web-UI example)
> **CIPP** — extract the patterns worth reusing, and turn them into a reasoned
> **architecture recommendation** for `m365-configurator`.
>
> **Tenets under test:** minimal dependencies (NFR-3); containerized &
> portable, Linux + PowerShell 7 (NFR-4); no credential persistence / nothing
> phones home (NFR-1, NFR-2); audit-grade logging (NFR-5); loud/fast failure
> (NFR-6); syntax-stability & pinned versions (NFR-7); readability &
> diff-friendly output (NFR-9).
>
> **Decisions / questions informed:** **Q1** (core language/runtime), **Q2**
> (interface), **Q8** (profile format), **Q9** (profile sharing/versioning).
> Everything here is a **recommendation for the design checkpoint** — the final
> calls are made with the owner, and each becomes an ADR in `docs/decisions/`.
>
> **Author:** research sub-agent · **Date:** 2026-07-22
>
> Every nontrivial claim is cited inline `[n]`; see [Sources](#10-sources).
> Sibling docs cross-referenced by filename; Microsoft365DSC engine internals

## 1. How to read this doc

This is a **prior-art** study, not a feature spec. For each tool we record the
same facets so they compare cleanly: **purpose · language/runtime ·
baseline/config representation · dry-run/what-if · drift detection ·
remediation (assess-only vs corrects) · reporting/output · interface · auth
model · container/Linux friendliness.** We then distil the recurring patterns
and map them onto our open questions.

Two framing points carried over from the sibling research:

- Our dry-run/drift engine cannot lean on `-WhatIf`; it must be
  `Get → normalize → structural diff → render` (see
  `docs/research/01-microsoft-graph-surface.md` §6). Prior art confirms this is
  the norm, not a workaround.
- Auth is settled: interactive-delegated + device-code, **memory-only tokens**,
  aggressive cleanup (ADR-0001; `docs/research/04-authentication-and-credential-cleanup.md`).
  Several prior-art tools take the opposite stance (stored app secrets /
  refresh tokens), which is exactly why we survey them as *contrast*.

## 2. TL;DR — the load-bearing findings

1. **The whole field is PowerShell.** Every serious M365 posture tool is a
   PowerShell module or is driven by one — ScubaGear, Maester, Monkey365 and
   Microsoft365DSC are PowerShell [1][4][7][9]; even CIPP, the lone web app, is
   a React front-end over a **PowerShell** Azure Functions backend [10][12].
   This strongly favours a **pure-PowerShell-7 core (Q1)** — a non-PowerShell
   front-end buys nothing the modules don't already give us and adds a runtime
   to trust (NFR-3).
2. **Assessment and remediation are almost always separated.** ScubaGear,
   Maester and Monkey365 **assess only** — they never write to the tenant
   [1][4][7]. Only Microsoft365DSC (declarative) [9] and CIPP (imperative) [11]
   remediate, and both make it an explicit, opt-in action. This validates our
   split of **read-only dry-run/drift** from an **explicit apply** (FR-8/9/10/11).
3. **A self-contained HTML report is the universal review artifact.** ScubaGear,
   Maester and Monkey365 all emit an interactive **HTML** report (plus JSON/CSV)
   [1][5][8]. That is how they deliver "satisfying to review" **without** a live
   server — directly relevant to **Q2**.
4. **Config/baseline formats already cluster on YAML + JSON.** ScubaGear's config
   file is **YAML or JSON**, generated by `New-SCuBAConfig` [3]; Maester and
   Monkey365 rules are JSON [7][8]; only Microsoft365DSC uses PowerShell/`.psd1`
   + MOF [9]. This points **Q8** at YAML-for-humans / JSON-as-canonical.
5. **ScubaGear is Windows-only and PowerShell-5.1-bound** — a cautionary tale.
   It is pinned to a library that only runs on Windows PowerShell 5.1, so it
   "will only run on Windows" [2]. Our Linux + pwsh 7 tenet (NFR-4) means we
   must **not** inherit that class of dependency — favouring the REST-based
   Graph/EXO modules (docs 01/02) and treating Microsoft365DSC's runtime story
   as a live risk (see `docs/research/03-microsoft365dsc.md`).
6. **CIPP shows the model we must *not* copy.** It is a multi-tenant web portal
   that stores refresh tokens / app secrets in Azure Key Vault via the Secure
   Application Model and runs as an always-on Azure service (or a $99/mo hosted
   SaaS) [10][11][12]. Powerful for MSPs, but it violates our
   memory-only-tokens, no-persistence, single-engagement, no-phone-home tenets.
   It is prior art for **what a web UI costs**, not a template to follow.
7. **"Export → diff → apply → drift" is a proven loop.** Microsoft365DSC and
   CIPP both operationalise it; we should adopt the loop while implementing it
   on our own pinned Graph/EXO cmdlets and our own diff renderer.

## 3. Prior-art survey

### 3.1 ScubaGear (CISA)

**Purpose.** Automation that "verifies that a Microsoft 365 tenant's
configuration conforms to" CISA's Secure Cloud Business Applications (SCuBA)
baselines, across Entra ID, Defender/Security suite, Exchange Online, SharePoint,
Teams, Power BI and Power Platform [1].

**Language/runtime.** PowerShell — **but tied to Windows PowerShell 5.1**.
The dependency docs are blunt: at least one required library "is tied to
PowerShell 5… ScubaGear will only run on Windows" [2]. It also needs an external
**Open Policy Agent (OPA)** executable (tested v1.18.2), downloaded by
`Initialize-SCuBA` into `~/.scubagear/Tools` [2]. Module dependencies are
version-**range-pinned** (e.g. `ExchangeOnlineManagement 3.2.0–3.9.2`,
`Microsoft.Graph.Authentication 2.0.0–2.25.0`, `MicrosoftTeams`,
`powershell-yaml`) [2].

**Baseline/config representation.** Baselines are encoded as **Rego** policies
evaluated by OPA: PowerShell queries M365 APIs for settings, then OPA compares
them against the Rego rules [1]. The operator's own inputs live in a
**configuration file in YAML or JSON**, generated by `New-SCuBAConfig` and passed
via `-ConfigFilePath`; it carries `ProductNames`, `M365Environment`, tenant/auth
params, plus `OmitPolicy` (exclude a check, with rationale + expiry) and
`AnnotatePolicy` (attach remediation notes) [3].

**Dry-run/what-if · drift · remediation.** **Assessment only.** The first run
"does not make changes but helps you understand the default posture" [1]; there
is no apply, no drift-over-time, and no remediation.

**Reporting/output.** Interactive **HTML** report, structured **JSON**
(`ScubaResults`), and **CSV** export; omitted policies render gray/"Omitted"
[1][3].

**Interface.** CLI cmdlets: `Invoke-SCuBA`, `Initialize-SCuBA`,
`New-SCuBAConfig`, `Update-ScubaGear`, plus a `Start-ScubaConfigApp` GUI helper
for building the config file [1][3].

**Auth model.** Interactive sign-in and non-interactive **service principal +
certificate** (`Organization`, `AppID`, `CertificateThumbprint`) [3].

**Container/Linux.** **No** — Windows-only by construction [2]. This is the
single most important cautionary data point for our NFR-4.

### 3.2 Maester

**Purpose.** "Turns Microsoft security best practices into runnable tests so you
can make changes with confidence and prove compliance over time" — a
**Pester-based** test framework for Entra ID / M365 security config [5].

**Language/runtime.** PowerShell 7 + **Pester**; runs locally and in
**GitHub-hosted (Linux) runners** and CI [4][5].

**Baseline representation.** Security best practices expressed as **Pester
tests** (360+ built-in), grouped into baselines — CISA SCuBA, CIS M365, EIDSCA,
ORCA, and community tests [5]. Users add custom Pester tests to encode their own
policy. Tests are installed as files into your workspace via `Install-MaesterTests`
and refreshed with `Update-MaesterTests` — i.e. **tests-as-code you commit to a
repo** [4].

**Dry-run/what-if.** Notably, Maester ships **Conditional Access What-If**:
`Test-MtConditionalAccessWhatIf` calls the Entra CA What-If API to simulate a
sign-in scenario (user, app, location, device, risk) and report which policies
would apply — catching CA gaps *before* deployment [6]. Caveat: that API is
**beta and subject to change** [6].

**Drift detection.** Via **scheduled re-runs** (GitHub Actions / Azure DevOps /
Azure Automation) with email alerts when posture changes [5] — drift-as-CI
rather than a stored baseline diff.

**Remediation.** **None** — testing/monitoring only. Reports instead deep-link
to the relevant Microsoft admin portal for a human to fix [5].

**Reporting/output.** Interactive **HTML** report with drill-down + portal
links; also **Markdown, JSON, CSV, Excel** via `New-MaesterReport` [4][5].

**Interface.** CLI cmdlets: `Connect-Maester`, `Invoke-Maester`,
`Install-MaesterTests`, `Update-MaesterTests`, `New-MaesterReport` [4].

**Auth model.** `Connect-Maester` (delegated interactive, national-cloud aware
via `-Environment`); in CI, **Workload Identity Federation** so no secrets are
stored/rotated [4][5]. Delegated-interactive aligns with our ADR-0001.

**Container/Linux.** **Yes** — pure PowerShell, runs in Linux CI runners [4][5].

### 3.3 Monkey365

**Purpose.** Security-assessment framework for M365, Azure and Entra ID that
"helps identify misconfigurations, review cloud security posture" [7].

**Language/runtime.** PowerShell (~98% of the repo), explicitly **self-contained
with bundled dependencies and no dependency on external Microsoft modules**; runs
on Windows PowerShell **and PowerShell Core cross-platform**, with a **Dockerfile**
shipped [7][8].

**Config/rule representation.** A **collector-based** architecture (Exchange,
SharePoint, Teams, Purview, Fabric…) feeds a rules engine whose rulesets map to
**CIS Microsoft 365 Foundations** and **CIS Azure Foundations** benchmarks;
custom rulesets are supported [7][8].

**Dry-run/what-if · drift · remediation.** **Assessment only** — collect and
score against benchmarks; no apply, no drift-over-time, no remediation [7][8].

**Reporting/output.** **HTML** report plus **JSON, CSV, and CLIXML** (the last
for PowerShell pipelines) [7][8].

**Interface.** Single primary cmdlet `Invoke-Monkey365` with parameters like
`-Instance`, `-Collect`, `-ExportTo`, `-IncludeEntraID`, `-PromptBehavior`,
`-Environment` [7][8].

**Auth model.** Broadest of the group: **web-browser interactive, device code,
service principal, certificate, and ROPC (username/password)** [8]. Interactive
+ device-code line up with ADR-0001; ROPC we would never use (see doc 04 §8).

**Container/Linux.** **Yes** — PowerShell Core + shipped Dockerfile [7][8].
The "self-contained, no external module dependencies" design is an interesting
minimal-deps counterpoint (it vendors its own collectors instead of taking a
dependency on `Microsoft.Graph`/EXO).

### 3.4 Microsoft365DSC (prior art for the *pattern*)

> Engine internals, resource coverage, MOF/credential handling and the
> Linux/pwsh-7 verdict are analysed in
> `docs/research/03-microsoft365dsc.md`. Here we record only what it teaches as
> a **pattern** for export/drift/remediation.

**Purpose.** Manage M365 tenants as **infrastructure-as-code** via PowerShell
Desired State Configuration [9].

**Representation.** **Declarative desired state**: configurations are PowerShell
(`.ps1`) compiled to **MOF**, with configuration *data* separated from logic [9].
The desired state *is* the profile.

**The loop — this is the reusable idea.** Three cmdlets embody a clean lifecycle
we should mirror [9]:

| Stage | Microsoft365DSC cmdlet | Our analogue (FR) |
|---|---|---|
| **Export** tenant → config | `Export-M365DSCConfiguration` | Export → profile (feeds FR-5) |
| **Test** desired vs actual (drift) | `Test-M365DSCConfiguration` | Drift detection (FR-10) |
| **Apply / correct** | `Start-M365DSCConfiguration` | Apply / remediate (FR-9/FR-11) |

**Remediation.** **Yes, declarative** — `Start-M365DSCConfiguration` applies the
config and auto-corrects drift; idempotency is inherent to the DSC model (Test
then Set) [9]. This is exactly the "deterministic remediation" shape FR-11 wants.

**Auth model.** Credentials, **certificate (AppId + Thumbprint)**, or service
principal [9] — app-centric, which is in tension with our delegated/device-code
decision (flagged in ADR-0002 and doc 03).

**Container/Linux.** Repo ships Dockerfile(s); DSC's traditional dependence on
the Local Configuration Manager / MOF has historically bound it to Windows
PowerShell — **the open question doc 03 resolves.** Treat as unverified here [9].

**Why it matters to us.** Even if we do **not** adopt the DSC engine (ADR-0002 is
only *Proposed*), the **export → test → apply** decomposition and its inherent
idempotency are the blueprint for our custom engine.

### 3.5 CIPP (contrast — a web-UI, multi-tenant admin tool)

**Purpose.** The CyberDrain Improved Partner Portal: a **multi-tenant** M365
management portal aimed at MSPs, for user management and "deploying your own
preferred standards" across many client tenants [10].

**Architecture / runtime.** A **React** front-end (repo is ~99% JavaScript) over
a **PowerShell**-driven API running on **Azure Functions + Static Web Apps** —
i.e. an always-on serverless web service, not a CLI [10][12].

**Deployment / hosting model.** **Self-hosted in the MSP's own Azure
subscription** (paying Azure consumption, commonly \$10–30/mo) **or** a
**sponsor-hosted SaaS** at ~\$99/mo where CyberDrain runs the infrastructure and
updates [12]. License is **AGPL-3.0** [10].

**Config/baseline representation.** **Standards Templates**: reusable baselines
assigned to All-Tenants, tenant groups, or single tenants, with a specificity
hierarchy for conflicts [11]. **Drift Management** (v8.3+) templates add finer
handling of anything out of alignment [11].

**Dry-run/what-if · drift · remediation.** Standards run on one of three
actions — **Report, Alert, or Remediate** — **reapplying every 12 hours**;
`Remediate` actively rewrites tenant config to match the template [11]. Drift
Management evaluates **every 12 hours** and defaults to Report/Alert, with an
optional toggle to auto-remediate (and to permanently deny a drift so future
occurrences self-heal) [11]. So CIPP both **detects drift and remediates** — but
on a **scheduled, unattended** cadence, not an interactive dry-run-then-apply.

**Auth model — the sharp contrast.** CIPP uses the **Secure Application Model**:
long-lived **refresh tokens and app secrets stored in Azure Key Vault** so the
service can act against every managed tenant unattended [11][12]. This is the
polar opposite of our memory-only, wipe-on-exit stance (ADR-0001, NFR-1).

**Container/Linux.** N/A in our sense — it is an Azure-hosted web service, not a
portable CLI container [10][12].

**Takeaway.** CIPP is the reference for **what a web UI + multi-tenant
automation costs**: a persistent service, stored long-lived credentials, an
Azure dependency, and a hosted-SaaS option that "phones home" by design. Every
one of those is a tenet violation for us — which is the clearest argument
**against** a CIPP-style web UI for the MVP (see Q2).

| Output | HTML/JSON/CSV [1] | HTML/MD/JSON/CSV/Excel [5] | HTML/JSON/CSV/CLIXML [8] | config files/logs [9] | web UI [10] |

**Reading the table.** The two tools whose runtime + auth posture most resemble
what we want are **Maester** and **Monkey365** (pure pwsh, cross-platform,
interactive/delegated, no stored secrets, HTML report). Neither remediates — so
for the *write* half of our product, **Microsoft365DSC** is the pattern to learn
from, and **CIPP** is the anti-pattern to avoid.

## 5. Pattern extraction

What the survey teaches, mapped to the engines we must build.

### 5.1 Representing desired state

- **Data, not code, is the durable choice.** ScubaGear (YAML/JSON) [3] and the
  rule-driven tools [7][8] keep desired/expected state as **declarative data**;
  only DSC uses executable config [9]. Data is safer to share (no code
  execution), easier to diff, and trivially "config-only" (FR-5) — favouring a
  **data profile format (Q8)** over a `.ps1`.
- **Separate the baseline from the tenant-specific overlay.** ScubaGear splits
  the fixed Rego baseline from a per-run config file carrying exclusions and
  annotations [1][3]; CIPP layers All-Tenants → group → tenant standards [11].
  We want the same seam: a **shared baseline profile** plus a thin **per-tenant
  overlay** (name remaps, break-glass exclusions) — this is where FR-7
  name-remapping lives.

### 5.2 Separating assessment from remediation

- Three of five tools are **assess-only** [1][4][7]; the two that write make it
  an **explicit, named action** (`Start-M365DSCConfiguration`; CIPP's
  `Remediate`) [9][11]. Our FR-8→FR-9→FR-11 progression (dry-run → apply →
  remediate) is squarely in the mainstream, and the **read-only default** keeps
  the dangerous path opt-in (mirrors our read/write scope split, doc 01 §3).

### 5.3 Dry-run / what-if UX

- **Nobody trusts a generic `-WhatIf` as the preview.** The strongest preview in
  the field is Maester's **domain-specific simulation** —
  `Test-MtConditionalAccessWhatIf` against the CA What-If API [6] — not the stock
  ShouldProcess switch. This corroborates doc 01 §6: our dry-run must be a
  **real, property-level diff** we render ourselves, optionally augmented by the
  CA What-If API as a *pre-apply safety check* for Conditional Access.
- **Show a clear pass / needs-attention signal.** ScubaGear's gray "Omitted",
  Maester's pass/fail counts — a scannable verdict at the top, detail below
  (FR-8's "clear pass/needs-attention signal", NFR-9).

### 5.4 Drift reporting

- Two cadence models exist: **stored-baseline diff** (Microsoft365DSC `Test-`)
  [9] vs **scheduled re-scan** (Maester CI, CIPP every 12h) [5][11]. For a
  per-engagement CLI tool the **stored-baseline diff** is the right primary
  model (drift = profile vs live), with scheduled runs as an optional wrapper.
- **Drift output should reuse the dry-run renderer.** CIPP treats "what's out of
  alignment" and "what remediation would do" as the same object [11]; we should
  render **drift and dry-run with one diff formatter** so reviewers learn one
  format (NFR-9).

### 5.5 Idempotency

- DSC's **Test-before-Set** makes re-apply a no-op when already compliant [9] —
  the gold standard for FR-11 "deterministic". Our engine reproduces this
  manually: match existing objects (by `displayName`/stable key), `PATCH`
  singletons, and only create what's missing — exactly the rules enumerated in
  `docs/research/01-microsoft-graph-surface.md` §7 and the policy+rule pairing in
  `docs/research/02-exchange-online-surface.md`.

### 5.6 Name / GUID handling

- ScubaGear's exclusion lists reference objects, and CA/EXO objects are
  name/GUID-scoped and tenant-specific (docs 01/02). Prior art doesn't solve
  cross-tenant portability for us — **name remapping (FR-7) is our
  differentiator.** Store profiles by **stable name / well-known id**, resolve to
  tenant GUIDs at apply time (doc 01 §7 rule 9).

### 5.7 Readable output

- The **self-contained interactive HTML report** is universal [1][5][8] because
  it is portable, needs no server, and is pleasant to scan. We can adopt it as a
  **generated artifact** (dry-run/drift report) without standing up a web app —
  the key insight for Q2. Machine-readable **JSON** always ships alongside for
  automation/diffing [1][7].

## 6. Recommendations toward Q1 / Q2 / Q8 / Q9

> These are **recommendations for the design checkpoint**, with trade-offs
> stated. The owner makes the final call; each resolved question becomes an ADR.

### 6.1 Q1 — Core language/runtime → **recommend pure PowerShell 7**

**Recommendation.** Build the tool as a **pure PowerShell 7 module/app**; do not
wrap it in a Python/Go/Node front-end that shells out to `pwsh`.

**Why.**
- The entire configuration surface *is* PowerShell (Graph SDK, EXO, possibly
  Microsoft365DSC — docs 01/02/03). Every prior-art engine is PowerShell, and
  the cross-platform ones (Maester, Monkey365) are **pure** PowerShell running on
  Linux [4][7]. Even CIPP's *backend* is PowerShell [12].
- A second-language front-end adds a runtime to install, trust, and pin (against
  **NFR-3**), plus a process/serialization boundary to `pwsh` that becomes one
  more thing to break when cmdlet output shape changes (against **NFR-7
  syntax-stability**). It buys only UI ergonomics — which Q2 solves differently.
- Pure pwsh keeps the container minimal (one runtime), and testing is
  first-class via **Pester** (as Maester demonstrates) [4].

**Trade-off / mitigation.** PowerShell's interactive-UI story is thinner than
Node/Go. That is acceptable because Q2 recommends a CLI + generated HTML report,
both of which pwsh does well. If a richer TUI is later wanted, add a *single*
well-scoped module rather than a whole new language runtime (justified per
NFR-3).

### 6.2 Q2 — Interface → **recommend CLI-first + generated HTML/Markdown report; defer/avoid a live web UI**

**Recommendation.** A clean **verb-noun CLI** as the control surface, which
**emits a self-contained HTML (and Markdown/JSON) report** for dry-run and drift
review. Optionally add a lightweight **TUI menu** for profile selection later. Do
**not** build a locally-served web UI for the MVP.

**Why.**
- The "easy and satisfying to review" goal is met by prior art through a
  **generated interactive HTML report**, not a live server — ScubaGear, Maester
  and Monkey365 all do exactly this [1][5][8]. We get the visual payoff with zero
  server, zero bound port, zero browser dependency in-container.
- A live web UI is the **CIPP path**: an always-on service, a larger attack
  surface, and (in CIPP's case) stored long-lived credentials [10][11][12] — in
  direct tension with NFR-1/NFR-2, minimal-deps (NFR-3), and the ephemeral
  one-shot container leaning (Q3). Device-code auth (ADR-0001) is also a natural
  CLI flow, not a web-form flow.
- CLI is what every cross-platform tool in the survey chose [1][4][7][9], and it
  composes cleanly into CI if scheduled drift is ever wanted (Maester's model).

**Trade-off / mitigation.** A CLI is less point-and-click than CIPP. Mitigate
with (a) a rich, colourised, aligned diff renderer (NFR-9), (b) the HTML report
artifact for stakeholders, and (c) an optional TUI selection menu — all
achievable in pwsh without a web stack. Revisit a *read-only* local web report
viewer only if the checkpoint wants it, keeping it strictly offline.

### 6.3 Q8 — Profile format → **recommend YAML for humans, JSON as the canonical serialization**

**Recommendation.** Author and share profiles in **YAML**; **canonicalize to
JSON internally** (stable key ordering, sorted arrays) for diffing and as the
export/interchange format. Keep `.psd1` as a viable runner-up if the checkpoint
weights minimal-deps above reviewer familiarity.

**Why.**
- The field already clusters here: ScubaGear's config is **YAML or JSON** [3];
  Maester/Monkey365 rules are **JSON** [7][8]. Only DSC uses PowerShell data +
  MOF [9], which is code-shaped and less friendly to non-PowerShell reviewers.
- Against the tenets: profiles must be **human-readable, diff-friendly,
  config-only** (FR-5, NFR-9). **YAML** wins readability (comments, low syntactic
  noise, block structure) — decisive for the "a reviewer can scan a profile and
  know what it means" goal. **JSON** wins as the canonical machine form: it is
  the native shape of Graph request bodies (doc 01), and deterministic JSON diffs
  keep drift/dry-run output stable (NFR-9).
- Both are trivially **config-only** — no risk of embedding executable logic
  (unlike a `.ps1`).

**Trade-offs.**
- YAML needs a parser dependency (`powershell-yaml`, the same module ScubaGear
  pins [2]) — a real but small, pinnable NFR-3 cost.
- **`.psd1`** avoids any parser dependency (native `Import-PowerShellDataFile`,
  which reads *data only*, not arbitrary code) and is idiomatic pwsh — attractive
  under NFR-3, but less approachable for non-PowerShell collaborators and noisier
  to diff for deeply nested objects. If minimal-deps is weighted highest, `.psd1`
  is the fallback.
- **JSON-only** is the simplest (zero extra deps, native
  `ConvertTo/From-Json`) but loses comments, which hurts reviewability of a
  shared baseline. Hence YAML-for-authoring / JSON-as-canonical as the balance.

### 6.4 Q9 — Profile sharing/versioning → **recommend Git-committed profiles + single-file export for ad-hoc sharing**

**Recommendation.** Treat profiles as **version-controlled files in Git** — the
Maester "tests-as-code you commit" model [4] — and support **single-file
export/import** (one YAML/JSON) for the "upload an exported profile" path the
vision and FR-6 call for. Version a **known-good baseline** as a **tagged
release** of the profile so `v1 → v2` diffs are reviewable in the normal PR flow.

**Why.**
- Profiles are **config-only, never credentials** (FR-5, NFR-1), so committing
  them to Git is safe — unlike CIPP, which must vault its secrets [11]. This is a
  direct benefit of our no-persistence tenet.
- Git gives us history, blame, PR review, and tags "for free" — the most
  readable, auditable versioning available (NFR-5/NFR-9), and it matches how
  Maester expects tests to live [4].
- Single-file export satisfies collaboration without requiring the recipient to
  clone a repo (FR-6, vision's "import an exported file").

**Structure recommendation (for the checkpoint).**
- The **shipped reference baseline** lives in *this* repo under `profiles/`
  (e.g. `profiles/security-baseline/`), versioned with the tool.
- Consumers keep **their own** profiles in **their own** repo/location; the tool
  loads a profile by path or from an exported file — keeping tool and profiles
  **loosely coupled** so a profile can be shared without shipping the tool.
- A "known-good baseline" = a **git tag** on the profile (e.g.
  `baseline-1.2.0`), enabling drift-vs-tag and baseline upgrade diffs.

**Trade-off.** A separate profiles repo is cleaner for multi-consumer sharing but
adds a moving part; bundling the reference baseline in-repo is simpler for the
MVP. Recommend **in-repo reference baseline now**, leave "promote to its own
repo" as an easy later move.

## 7. Candidate architecture

A concrete sketch to anchor the checkpoint discussion — a **pure PowerShell 7
module** (Q1) driving the pinned Graph/EXO cmdlets from docs 01/02, implementing
the Microsoft365DSC **export → test → apply** loop [9] on our own diff engine.

### 7.1 Component shape

```
m365-configurator/                (pure PowerShell 7 module)
├─ src/                           public cmdlets (verb-noun CLI, Q2)
│   Connect-M365Session           interactive/device-code, -ContextScope Process (doc 04)
│   Export-M365Profile            read tenant → normalized profile (YAML)      [FR-5]
│   Invoke-M365DryRun             Get→normalize→diff→render (no -WhatIf)        [FR-8]
│   Invoke-M365Apply              explicit go-ahead; ordered idempotent write  [FR-9]
│   Test-M365Drift                profile vs live, reuse diff renderer          [FR-10]
│   Invoke-M365Remediation        deterministic, previewable via dry-run       [FR-11]
│   Get-M365Log                   in-tool access to structured logs            [FR-12]
│   Invoke-M365Cleanup            token/secret purge (doc 04 §5)               [FR-3]
├─ engine/                        diff / normalize / dependency-ordered plan
├─ profiles/                      YAML profiles (config-only); JSON canonical  [Q8/Q9]
│   └─ security-baseline/         shipped reference baseline (git-tagged)
├─ reports/                       generated self-contained HTML/MD artifacts   [Q2]
└─ Dockerfile                     one-shot CLI container, pwsh 7 on Linux       [NFR-4]
```

### 7.2 The export → diff → apply → drift loop

1. **Connect** (device-code by default in-container; memory-only tokens;
   read-only scopes for scan, escalate to write only on apply — docs 01 §3,
   04).
2. **Export** the live tenant to a normalized **profile** (YAML), stripping
   read-only/server fields and storing objects by **stable name** for
   remapping (docs 01 §7, 02). This is our `Export-M365DSCConfiguration`
   analogue [9].
3. **Dry-run / drift** = `Get current → normalize both sides → structural diff →
   render`. One renderer produces the **CLI diff + HTML/JSON report**; a clear
   pass/needs-attention verdict on top (FR-8/FR-10, NFR-9). Optionally call the
   CA **What-If** API as a pre-apply safety check for Conditional Access [6].
4. **Apply / remediate** only after explicit go-ahead: a **dependency-ordered**
   plan (e.g. security-defaults-off → named-locations → CA policies — doc 01
   §7), idempotent (match-by-name / PATCH singletons), per-item success/failure,
   loud on partial failure (FR-9/FR-11, NFR-6). Deterministic remediation is the
   same apply engine scoped to the drifted items.
5. **Log** every change-applying action as structured JSON to an ephemeral,
   RAM-backed dir; retrievable via `Get-M365Log` (FR-12, NFR-5). **Clean up**
   tokens/secrets in a `finally` (doc 04 §5); container discard is the backstop.

### 7.3 Where the DSC decision plugs in

ADR-0002 is still *Proposed*. This architecture is **engine-agnostic at the
seam**: if `docs/research/03-microsoft365dsc.md` + a container proof clear
Microsoft365DSC on Linux/pwsh-7 and auth (Q7), `Export/Invoke-M365*` can delegate
to `Export-/Test-/Start-M365DSCConfiguration` [9]; if not, the same cmdlets run
our **custom Graph/EXO engine**. Either way the CLI, profiles, reports, logging,
and cleanup — the parts this doc recommends — are unchanged.

## 8. Key takeaways / recommendations

- **Q1 → pure PowerShell 7.** The whole ecosystem is PowerShell [1][4][7][9][12];
  a second-language front-end only adds runtime/dependency/stability cost
  (NFR-3/NFR-7) for UI polish that Q2 delivers another way.
- **Q2 → CLI-first + generated self-contained HTML/Markdown report; avoid a live
  web UI for MVP.** The HTML *artifact* (ScubaGear/Maester/Monkey365) gives the
  "satisfying review" without a server; CIPP shows a web UI's true cost —
  persistent service + stored long-lived credentials + Azure dependency
  [10][11][12], all tenet violations.
- **Q8 → YAML for humans, JSON as canonical.** Matches where the field already
  is [3][7][8], best serves readability + diff-friendliness (NFR-9); `.psd1` is
  the minimal-deps fallback.
- **Q9 → Git-committed profiles + single-file export; baselines as git tags.**
  Safe precisely because profiles are credential-free (FR-5/NFR-1), unlike CIPP's
  vaulted secrets [11]; mirrors Maester's tests-as-code model [4].
- **Reuse the DSC loop, not necessarily the DSC engine.** Export → test → apply
  with inherent idempotency [9] is the blueprint; implement it on pinned
  Graph/EXO cmdlets and our own diff renderer (docs 01/02).
- **Assess read-only by default; make writes explicit.** The assess-only
  majority [1][4][7] validates our dry-run/drift-then-apply split and read/write
  scope escalation (doc 01 §3).
- **Build a real diff, don't trust `-WhatIf`.** The best previews in the field
  are domain-specific simulations (Maester CA What-If) [6], not stock
  ShouldProcess — consistent with doc 01 §6.
- **Heed the ScubaGear runtime warning.** Its Windows/PS-5.1 lock-in [2] is the
  failure mode NFR-4 exists to prevent; prefer the REST-based, pwsh-7 modules
  (docs 01/02) and keep the DSC runtime question (doc 03) open until proven.
